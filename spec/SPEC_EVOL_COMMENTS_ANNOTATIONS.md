### 4.1 Identity and records

Host-boundary conformance proves that shadow/alias output cannot reach canonical commands; hash vectors prove scope binding, including distinct tenant/workspace IDs. The host supplies authenticated context, membership and resource authority; client claims, display names, a default scope or an admin flag do not substitute for them.

### 4.2 Anchor variants and stable resolution

An annotation has one stable primary resource and ordered canonical secondary resources, all in the same tenant/workspace. Roles, order, complete identities and version bindings enter the revision hash; ambiguous duplicates are rejected. Authorize every target for every action. Exact read/export is all-or-nothing: hiding a forbidden target cannot produce a purported complete hashed revision. A secondary-resource query uses the same rules as a primary query. Host partition fit is confirmed at the interface level by the final reviews; actual assignments and resolver evidence remain host qualifications.

Every target, anchor and discussion structural binding contains the frozen M1 source-version indicator. Preserve the checksummed optionality and evidence enums; the table describes meanings without reopening P1.

| Binding | Required facts | Applicability and review consequence |
|---|---|---|
| `observed` — observed at authorship | Immutable version or snapshot digest and evidence that this was the author's observed source. | Exact/current applicability requires authorized resolver equality. A changed source is stale; failed resolution is unresolved/unavailable. |
| `fixed-at-conversion` — fixed at conversion | Version/digest captured by conversion, conversion reference and explicit historical gap. | Can establish equality to that conversion baseline only. It never asserts what the original author saw or retrospectively validates that source. Display the conversion baseline and gap. |
| `unknown` | Explicit absence of an established observed version, with evidence/gap classification; no fabricated digest. | Historical content may be retained when otherwise admissible, but source applicability cannot be asserted and current-source validation is denied. |

Newly authored durable anchors require an observed immutable version or authorized snapshot. Imported surviving content may use the latter two variants without inventing history. Validation of current source from a conversion/unknown baseline requires explicit reanchoring into a new observed revision; a historical content assessment remains labeled as such. A matching current digest alone does not upgrade the indicator. All three variants, transitions by new revision and denial cases belong in the hash/applicability vectors, including free discussions without captures.

The model supports the following complementary anchors for arbitrary host resource kinds, including API-only creation:

| Anchor | Proposed stable representation | Failure behavior |
|---|---|---|
| Data/record | Resource reference and explicit source-version indicator; observed or conversion-bound cases carry the corresponding immutable version/snapshot digest. | Missing history is explicit; a missing/replaced resource is not substituted with a nearby record. |
| Field | Data anchor plus a versioned field selector. Prefer a stable field ID or JSON Pointer; repeated collections require stable element keys. | Reordering must not move a comment to another element. A pointer by position is valid only against the exact frozen source version. |
| Text | Data/document version, exact quote with prefix/suffix context, start/end offsets and declared normalization/offset units. Proposed units: Unicode code points with end exclusive. | Offsets are authoritative only for the recorded text version. | UI | Stable host surface/element key, resource binding, render/snapshot version and optional capture anchor. | Capture | Immutable host blob/document ID, digest, MIME type, intrinsic width/height, capture timestamp and coordinate-frame/crop metadata; optional data/UI anchor. | Missing, unauthorized or purged bytes make the capture unavailable. Never resolve a different image under the old reference. |

The host resolver returns explicit outcomes: exact match, source changed, unresolved/ambiguous, or unavailable, interpreted together with the stored version indicator. Public responses do not distinguish missing from forbidden resources. Resolver proposals require an explicit new revision to become anchors; a current DOM selection alone cannot become a durable validated anchor. Do not invent historical field/text/UI positions for imported content whose source is unknown.

Display the saved frame and version indicator; selecting a new live state requires explicit reanchoring into a new revision linked to the previous one. Imported historical bindings retain the limitations above.

Recheck on review/validation and AI dispatch, including queued dispatch; fail closed for current applicability when the host cannot establish it. Review applicability must not rely on a cached UI badge. Background invalidation may accelerate refresh but is not required for correctness and does not replace these checks; no generic daemon is required.

This defines generic requirements. The host owns its resource registry and source-to-resource/version mapping; comments owns source import unit/operation-to-canonical IDs/hashes/receipt history. Versioned import manifests bind the two without creating another editable contribution store. The HOST-D3 is decided; its domain mapping stays outside this SPEC. A neutral conformance case changes an opaque resource digest without any capture and must report stale applicability, independently of UI work.

### 4.3 Box and circle geometry

Proposed coordinate contract: an immutable frame with positive integral intrinsic pixel dimensions `W,H`, origin at top left, axes right/down, and a versioned transform for any crop. Rectangles use normalized `x/W, y/H, width/W, height/H`. Circles use normalized center `cx/W, cy/H` and radius `r/min(W,H)`; the canonical integer encoding below represents those normalized values. Both shapes reference the frame/capture digest, not the browser viewport. Decode the physical center as `(cx_norm*W, cy_norm*H)` and radius as `r_norm*min(W,H)`, then apply one aspect-preserving display transform with letterboxing/crop offsets. Do not scale the radius independently by viewport width and height. A `200x100` frame with center `(0.5,0.5)` and radius `0.1` renders at `(100,50)` with radius `10` intrinsic pixels.

Reject non-finite values, nonpositive sizes, out-of-frame shapes, missing frames and unknown schema versions. Persist shape IDs, ordering and semantic style with the revision. Zoom, device-pixel ratio, scroll and letterboxing affect rendering transforms only. Resizing capture bytes or changing a crop creates a new frame and revision. Pointer moves and undo/redo remain local draft operations until save.

Retain the frozen integer-millionth encoding, scale `S=1,000,000`, decoded as `v=q/S`. The shared quantizer accepts **base-ten decimal strings**, not JSON binary floating-point numbers. Preserve its frozen grammar: reject whitespace, exponent and leading-plus ambiguities; allow negative zero only as zero. Use exact rational/integer arithmetic and round ties upward (`"0.1234565"` becomes `123457`). Browser helpers call this same conversion; PG never rounds independently.

For a box, check exact input edges against the frame, quantize both endpoints of each axis, then derive width/height by integer subtraction. Do not round origin and width independently or silently clip. For a circle, require the entire disk inside the frame before and after quantization; check canonical containment with integer products and intrinsic dimensions using the shorter-dimension radius. Reject collapsed sizes, unsafe/fractional integers and any post-rounding violation rather than shrink the shape. Frame/crop dimensions and positions are intrinsic integers. Circle support is required; ellipse support would require a separate reviewed schema extension. These are encoding proposals, not measured operational limits.

### 4.4 Hashes, concurrency and history

The closed `record-kind` set for `revision-hash-v1` is: `annotation-revision`, `thread-structure-revision`, `comment-revision`, `review-event`, `prepared-submission-manifest`, `import-manifest`, `unit-receipt`, `batch-receipt-snapshot`, `lifecycle-event`, `operation-audit-event`, and `conversion-report`. Each uses SHA-256 over RFC 8785 canonical UTF-8 JSON with that discriminator and schema/hash version. Annotation/thread identities, current heads, tombstone/purge state, review applicability, idempotency indexes and delivery rows are mutable projections or infrastructure records, not additional hashed kinds.

Revision chains are keyed by full scope plus their stable annotation/thread/comment ID; review chains by full scope plus annotation ID across its revisions. Lifecycle events (tombstone, purge intent/outcome) chain per scoped object kind/ID; operation audit events (assignment, discussion state, archive/restore, account association) chain separately per scoped subject kind/ID, with principal/audience included where relevant. Each chain has a monotonic sequence and previous typed hash; batch snapshots chain per scoped batch. Submission/import manifests and unit receipts are standalone genesis records with explicit typed dependency links; conversion reports chain per host operation/inventory reference. No tombstone, lifecycle operation or audited state command implicitly edits content hashes.

Hash complete immutable scope, linkage and applicable body/profile/provenance material. Audit-event payloads remain minimal and policy-controlled; content, account projections, temporary URLs, loading state and derived applicability never enter another record's digest by accident. The server verifies blob digests/recomputes hashes and stores canonical bytes with indexed projections; client hashes are not authority. Validate byte-preserving PG reload.

Text/mention offsets count Unicode code points, end exclusive, against exact UTF-8 content with no implicit normalization; reject invalid surrogates. Technical registration instants use integer UTC epoch milliseconds, while source time follows section 4.5 and `EventEnvelope.ts` remains a string. Semantic numbers use schema-declared units and safe integers or canonical decimal strings; reject untyped floats. Absence differs from null; array order matters.

M1 already pins the `revision-hash-v1` corpus for all eleven kinds, canonical UTF-8 bytes and expected digests. Preserve it unchanged. Pure vectors cannot establish resolver mode, authenticated decisions or synthetic/real membership; companion command and host tests supply that evidence.

### 4.6 Bodies, mentions, profiles and bounded capacity

Preserve M1's tagged UTF-8 source bodies and hashed `specDigest` field. An active mention targets an opaque, scoped, authorized **principal**. A documentary attribution without a verified principal remains attributed text, not an active mention. Structured mentions contain exact source/display text and ordered, non-overlapping code-point spans over the reassembled logical body. Mentions grant no access; label resolution and notifications recheck authorization. A logical body may have ordered segments with exact bytes/digests and a whole-body digest. Format, segments, order, mentions and semantic profile belong to one revision, atomically visible only after complete assembly. Segments are not separate comments; complete authorized reads/export supply all of them. Body/segment/profile bounds remain host-injected, with proposed 64/16/16 KiB values. ## 5. Proposed authorization, validation and contest semantics

The host authenticates a principal, resolves authoritative tenant/workspace, verifies membership and checks every target/revision/capture for each action. Every query and relationship is scoped by both tenant and workspace; compound keys prevent cross-scope links. Never assume `tenantId === workspaceId`. Sentropic's comments boundary must use an uncached authoritative user-bound resolver and fail closed; E7's shadow/alias output cannot supply canonical identity. Qualify this boundary against ARCH-11 before the first real canonical write, including a real-data rehearsal. The required owner-signed tenant cutover must explicitly cover this boundary's first real write; OWNER-D1–OWNER-D4 and AUTH-M do not imply that signature or a global mode change. A transient tenant blocks activation.

Synthetic qualification uses explicit synthetic memberships/resources/policies and exercises the actual authorization mechanism without waiting for real assignments. Before any affected real entry, the host must establish real scope, attribution, visibility and any required redaction under its identified authority. Apply required redaction **before immutable registration**; a later redacted view cannot claim to be the complete hashed revision. This is a host intake gate from HOST-FINAL F-M2, not a new comments redacted-view API. Source custody follows the host's own lawful policy; OWNER-D4's remaining conversion-report rule applies to excluded legacy rows, with Immo backups outside this SPEC. The redaction gate creates no retention authority. Host attribution/visibility decisions are separate from OWNER-D1–OWNER-D4 and cannot be supplied by a conductor.

Define separate host-granted capabilities for read, comment, revise, assign, resolve discussion, review/validate, contest, resolve contest, shared archive/restore, personal/restricted archive, tombstone, purge and submit to AI. Creator/admin permission to close a thread does not confer validation permission. The generic layer checks invariants; the host supplies resource/role policy. Tools, jobs, imports/exports, receipt recovery, replay, attachment download and event subscriptions use this same seam and current permissions. User-label joins are authorized within scope.

Denied operations change neither revisions nor review history and emit no success event. Reads and ID-based mutations do not disclose foreign resources. Responses may distinguish 401/403 at the authentication/capability boundary and use a non-enumerating 404 for inaccessible object IDs. Stale expected versions/hashes return 409; malformed anchors/geometry return 400. Event payloads contain scoped references rather than unrestricted bodies; consumers refetch through authorization.

| Action/situation | Required interpretation |
|---|---|
| Submit for review | Append a submission event for one exact revision/hash; do not alter its content. |
| Validate | Append an authorized validation event for that revision/hash. Approval of revision A never means approval of B. |
| Contest | Append a contest referencing the reviewed revision/hash and the relevant review event. Preserve reason/evidence under retention policy. |
| Resolve or withdraw a contest/review | Append a linked event; do not edit/delete the original claim. The proposed conservative projection requires explicit renewed validation before displaying a contested revision as validated again. |
| New annotation revision | Keep all prior review/contest events as history. The new current revision starts without validation. Show an earlier validation only with its historical revision label. |
| Underlying source changes | Keep the historical revision and its review evidence. Its applicability to current data becomes stale; it cannot appear as validation of the new source. Reanchoring creates a revision that needs review. |
| Resolve/reopen discussion | Change discussion state only; never create, revoke or imply an annotation validation. |
| Tombstone | Make content unavailable and current validation inapplicable, while retaining permitted hash-linked history. |

Compute validation state from immutable events plus the selected revision and source-applicability state. Do not use one mutable `validated` boolean. Keep all contests visible in authorized history, including resolved ones. A delayed review on an older revision must remain attached to it and must not update the current revision's badge.

Separate generic mechanisms from effective policy values. Comments supplies injected capability checks, policy-version references and configurable review/adjudication projection; P1–P4 can implement and verify them using explicit synthetic policies. Synthetic roles, quorum and retention values are test fixtures, never deployed defaults. Deny unconfigured sensitive capabilities, including review, adjudication and purge. This draft selects no operational self-validation rule, quorum, contest-access matrix or retention duration.

Q3 requires effective values from the identified host policy authority before the corresponding sensitive capability is activated. Existing authorized policy may satisfy that gate; a new vote is not automatic. Sentropic P4-S and receiving-host P6 each need their applicable authority. Unconfigured review remains denied, but a review policy is not a blanket import prerequisite. Intake visibility/redaction and retention gates still precede affected real entries. The existing AI close/reassign/note assistant remains a discussion feature (E9).

G4 permits execution of a recorded authorized human decision through an injected comments decision-resolution port. It returns authenticated human actor/reference, exact action/scope, issue instant, expiry or explicit absence, revocation state/version and authority evidence. For review of an existing revision it binds that revision/hash. For an action creating a revision it binds the expected base revision/hash (or explicit absence plus expected aggregate version for creation) and a proposed-content digest. P1 defines that digest over the proposed immutable content/anchor/geometry/profile fields, excluding server-assigned registration, output hash and decision/executor envelope; execution compares the actual proposal and checks the base by CAS. The committed result records the decision and output separately, avoiding a hash cycle. Recheck current permissions, expiry/revocation and binding at execution; missing or mismatched evidence denies the action. Retry cannot invent a decision. Sentropic qualifies its binding, including E21's attestations, and every other host supplies its own; model output/service capability is not approval. Audit the human decision, optional agent proposal and actual executor/service/run separately. Track/engram freeze/promotion remains separately owned.

Shared archive/restore applies to an annotation or thread under the host's moderator policy. Personal/restricted archive is an audited principal/audience visibility preference for an already authorized audience; it grants no access and cannot archive for everyone. Both are version-checked and idempotent. Neither archives the associated subject automatically, resolves, validates, tombstones or changes retention. Archive stays outside content hashes, is reversible, and belongs to the P1 capability contract; the exact restricted audience is configured before host activation, not before hash-vector freeze. The final reviews record interface convergence on these meanings.

Logical storage includes identities, structural/comment/annotation revisions, review/contest events, source/capture references, manifests/receipts/import bindings, tombstone/purge receipts, idempotency and durable change delivery. Physical names/counts remain design details. Host IDs are opaque; package-owned keys enforce scope/hash integrity without host-domain foreign keys or user-deletion cascades through audit history. Do not delete/skip it, acknowledge undelivered success or mutate canonical audit history to unblock the cursor. Other scopes continue; the affected scope exposes a visible stalled status with an assigned outbox operator. If repair is unavailable it stays stalled, with no false replay progress. Qualify failure at the retry ceiling, restart, authorized retry, concurrent appends, strict ordering, deduplication and unaffected scopes; delivery quarantine, if used for diagnostics, is unrelated to legacy source-data exclusion.

Deliver stable event IDs with at-least-once retry and acknowledge only after delivery. Send-before-ack may redeliver; consumers deduplicate. Commit-before-NOTIFY loss recovers by polling. NOTIFY/SSE is a wake-up/transport, not durable truth; do not emit success independently from store, route and sink.

Expired cursors return explicit resync-required plus an authorized paginated snapshot tied to a new replay boundary. Reference PG and Sentropic binding require rollback, concurrent-commit, crash, restart, deduplication and expiry proofs. Publication failure cannot duplicate a revision/review on command retry.

### 6.3 Tombstones and retention

Canonical deletion is an **irreversible tombstone**, including before purge, with expected aggregate version, idempotency and immutable lifecycle event. Reversible hiding uses archive. Immediately deny payload reads, revision edits and AI submission; preserve only policy-permitted stable IDs/hashes/linkage and minimal audit. No restore command or import replay resurrects a tombstone; replies keep their root identity. Immo's OWNER-D4 exclusions do not become canonical tombstones or individual receipts: only their aggregate count enters the host-declared conversion report.

Keep immutable audit metadata separable from purgeable payloads. Purge must cover all affected historical bodies, quoted text, contest reasons/evidence, capture bytes, generated previews and derived indexes/caches according to the host retention policy. A retained digest is an integrity reference, not permission to retain or redisplay its original bytes and not a claim of anonymity. Shared capture/document objects require reference-aware deletion; removing one attachment must not destroy another authorized reference.

Source immutability does not exempt sources from retention/erasure or authorize copies. Each host applies authorized purge, holds and audit minimization to admissible payloads. Synthetic hold tests confer no real retention authority. Neither quarantine nor an invented hold may bypass OWNER-D4's legacy eradication for the owner-approved Immo scope; excluded rows cannot be imported. This is not an Immo backup prescription; Sentropic's cutover backup/restore is governed by its own lifecycle authority. Purge receipts distinguish erased, lawfully held and pending external/backup disposition and never claim inaccessible copies were erased. Do not present a live tombstone as backup/export/recipient erasure.

Operational tombstone atomically commits its record, immediate barrier, required audit/command result and effective journal changes. Add purge intent/jobs only when policy requires intent and purge authority is granted; otherwise tombstone succeeds without inventing intent. Later independently authorized intent is supported. History can report unavailable payloads. Workspace/account deletion invokes this lifecycle instead of implicit cascades (E5). Deleting a secondary resource alone must not erase a shared contribution/blob; mark its reference unavailable. Association withdrawal needs an authorized new revision and CAS; missing primary resources are not silently reparented. Whole-contribution tombstoning through a secondary target needs object-wide authority.

Immo's backups and their lifecycle are Immo's own domain and decision, outside this SPEC. Sentropic's own cutover backup/restore rehearsal belongs only to the later separate P4-S track under Q4; M2 and the path before Immo delivery have no such gate (M2-DELTA). Canonical-content, audit-identity, capture and AI/export policies remain host-owned; neither host's policy is silently imposed on the other.

P2 qualifies configurable retention/hold mechanisms with synthetic policies. Unconfigured purge stays denied; that is not a deployed retention policy or indefinite-retention permission. Before real-data lifecycle activation in P4-S/P6, identify effective policy, audit minimization and hold/purge authority. Tombstone alone does not authorize physical purge; the worker rechecks policy, scope and applicable holds.
