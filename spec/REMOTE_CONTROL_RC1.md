# RC1 session authority

This implements the sentropic RC1 boundary from plan v1.1 revision 2 and the frozen joint interface, SHA-256 `104e64761f957c12291ad86bc8553359d63bf15135660d7f53ddbdccded17032`. RC2 supplies the approved native mapping/capsule; K-app and K-native supply dispatch, claim, durable consumption and effects. No action routes or provider effects are enabled by RC1.

The standalone IdP owns `POST /api/v1/auth/session/remote-action-evidence`. The product root returns `403 authority_refused`. The issuer route requires TLS, an exact authenticated app workload, and the `remote.evidence.issue` S2S scope and pinned resource. Browser Origin/cookies are refused before body parsing. Input is streamed with an 8192-byte maximum, duplicate-key and invalid UTF-8 rejection, and a closed EvidenceRequest. Responses use `no-store`; failures contain only typed codes.

The issuer derives the owner and original authentication time from the current verified session credential. It independently resolves the native target's tenant/workspace membership. A global login may switch approved native targets without a new login or MFA ceremony. Every explicit action gets fresh EdDSA evidence with exact action/target/operation/payload/nonce bindings and a unique jti, bounded to 60 seconds and the original credential expiry. Issuance replay metadata is namespaced in the existing unique proof-fence table for at least 90 days. K-app dedup and native durable jti/nonce consumption remain independent obligations.

`authorizeRemoteAction` requires approved-owner equality, current exact-workspace membership, a permitted nonviewer role, enabled control epoch and current BindingControlConsent. Only that consent supplies `remote.input` and `remote.permission.respond`. Owner-wide on or an administrator role grants no scope. Input additionally requires interactive mode and no auto-approval policy. The attestation has the exact frozen fields, with no envelope/self-digest cycle.

`verifyRemoteCliProof` compares the complete source-signed proof against a trusted current-native-state port, including the closed Target, approved-registration revision, provider identity, mode/policy, capabilities, key and deadline. The default production target contribution is unavailable. Tests inject the native port; synthetic results do not close installed/native acceptance.

## Isolated authority

| Workload | Private authority | Public input / allowed purpose |
| --- | --- | --- |
| Standalone IdP | Its session-signing secret, issuer-private session volume and IdP evidence key | Current login verification; exact-action evidence only |
| App authorization | Its attestation key and app workload credential | Public IdP/source trust; current membership/consent attestation |
| App mesh instruction | Its mesh instruction key | Public trust; eventual action-envelope signing in K-app |
| Native B | Enrolled source/native keys and local state | Public IdP/app/mesh trust; independent verification and durable consumption |

The three proof-signing roles require distinct public fingerprints, kids, workloads and secret references. The loader requests only its own role's secret and compares its derived public key with pinned public trust. Public configuration rejects private key fields. Unknown/revoked or substituted keys fail validation; rotation installs acknowledged public trust before activation. No fixture private key is committed.

BRRC1-EX1 adds a dedicated `auth-idp-session-signing` Secret reference and `auth-idp-session-authority` PVC to the IdP manifest. The product receives neither. Session and refresh credentials cryptographically bind original MFA, authentication time and session version; refresh preserves them and rotates with a credential-hash CAS. Old credentials without signed lineage cannot authorize remote control; pre-upgrade UUID refresh credentials require a new login.

The issuer-private volume retains current credential hashes, immutable login metadata, expiry and revocation tombstones. It stores no bearer or proof bytes. Login/refresh/revoke update this authority; a restored or modified shared DB row cannot create, elevate or revive successfully tombstoned authority. Writes use per-session filesystem fences, fsync and atomic replacement. An interrupted writer leaves authority closed for recovery. An ambiguous refresh fails closed and can require a new login. Tombstones are retained without automatic deletion. Session-store loss/corruption refuses authority and prevents IdP login/refresh completion. Restoring an older private authority volume requires a separately qualified revocation/epoch recovery and remains closed until that gate passes.

Bulk session revocation tombstones every deleted session ID, including a login whose private creation has not completed. A tombstone for an unknown ID prevents that creation from reviving deleted authority. Evidence preparation revalidates current login after asynchronous target/replay work; the final synchronous EdDSA signature shares the per-session private revocation fence and rechecks the original conservative deadline. Revocation and signing therefore have an explicit ordering boundary across issuer processes.

Revocation order is DB deletion first, then guarded issuer tombstones, for both session-manager and OAuth single/bulk ports. A stale lock, corrupt file or missing PVC cannot prevent DB row removal. Each known deleted ID is attempted before the user scan. A private-store failure latches the issuer process closed, including after shared-row restoration or filesystem repair. Local logout completes; recovery is logged with a typed code. The mount must already exist: missing storage is never replaced with an ephemeral directory. Before restarting a failed issuer, the operator must restore trustworthy private storage and replay affected revocations; clearing a lock alone is not recovery.

Product-originated revocations use `POST /api/v1/auth/session/remote-revocations` on the standalone IdP. Token acquisition uses the matching public HTTPS issuer; delivery uses the existing `http://auth-idp:8787` ClusterIP service. An exact S2S client/subject, pinned resource and `remote.sessions.revoke` scope remain mandatory. A domain-separated HMAC-SHA256 using the S2S client secret binds POST, path, timestamp/random nonce, authorization and exact body bytes. The issuer accepts stamps within 30 seconds; revocations are idempotent. It authenticates the 204 acknowledgement under a separate MAC domain bound to that request, only after private tombstones are durable. A forged 204 cannot clear the product's pending intent. This deny-only hop carries session/user IDs and a short-lived scoped token, never the client secret. The internal hop provides authentication/integrity, not confidentiality. Public HTTP stays refused even with forged forwarded-proto; no forwarded header establishes trust. Browser requests, token substitutions, oversized/ambiguous bodies and nonclosed inputs are refused.

Canonical session/OAuth deletion and destructive account deletion atomically persist credential-free pending intents in the existing settings store (disjoint `remote_session_revocation:` keys, no user/workspace foreign key). Only an authenticated issuer acknowledgement removes an intent. Logout, logout-all and account/admin endpoints return `503 { error: authority_unavailable, revocation: pending }` on unavailable delivery, clear session/refresh cookies and retain the committed DB deletion. The existing approval sweep drains up to 20 pending intents on product startup and every 15 minutes, including when no approvals expire, stopping on the first unavailable delivery. No in-memory queue is required for restart recovery. DB absence refuses current remote authority; an unacknowledged delivery still requires retry before shared-DB restore or issuer recovery and is not a completed durable revocation. No instantaneous offline/native revocation is claimed.

The default-deny ingress baseline admits this service hop only from the same namespace's `sentropic/api` pods to `sentropic/auth-idp` TCP 8787 through `allow-api-to-auth-idp`. Manifest selftests pin that policy and the existing Service/Deployment selectors and port. F6 changes manifests only; no live provisioning or apply is performed.

Account self-deactivation, admin disable and approval expiry use the same issuer revocation boundary. Physical account deletion captures deleted session IDs inside the destructive transaction and sends issuer tombstones only after commit; connector grant teardown and issuer delivery are both attempted. Failed delivery cannot roll back account/workspace/session destruction. The approval sweep removes every selected user's DB sessions before sending any issuer request, attempts every user independently, logs failed deliveries for recovery, and preserves its completed expiry count.

## Configuration and composition handoff

The standalone issuer requires its isolated `JWT_SECRET`, `REMOTE_ACTION_ROLE=auth-idp`, and `REMOTE_ACTION_SESSION_STATE_DIR` on the issuer-only durable mount. The preprod deploy job runs a read-only preflight before `make k8s-deploy-preprod`: missing/invalid isolated signing material, absent shared `OAUTH_SIGNING_KEK`, or an unbound PVC fails the job before any apply. The running Recreate workload remains untouched by that failed job. The shared KEK must remain identical for API and IdP so OAuth state/JWKS sealing does not fall back to their now distinct session secrets.

The conductor generates and stores signing material using the owner's .env procedure, then configures the following names. This branch generates/stores no deployment key and performs no deployment or workflow dispatch.

`.github/workflows/idp-session-secret.yml` follows `idp-workload-secret.yml`: dispatch-only, main-only, protected environment, private temporary manifest, server-side apply and unconditional cleanup. It validates the supplied signing material, materializes the named Secret, provisions only the issuer PVC and waits for `Bound`; it never applies the Deployment. On storage classes that defer binding until a consumer exists, the conductor must arrange qualified storage binding before CD; preflight continues to block workload apply. After provisioning, rerun the failed preprod deploy job. No `optional: true` or shared-session-secret fallback is introduced.

Configure `REMOTE_ACTION_REVOCATION_ISSUER`, `REMOTE_ACTION_REVOCATION_CLIENT_ID`, `REMOTE_ACTION_REVOCATION_CLIENT_SECRET` and `REMOTE_ACTION_REVOCATION_RESOURCE` in the existing `sentropic-api` Secret, inherited by the two workloads; the issuer URL must match IdP `OAUTH_ISSUER_URL`. The credential belongs to an owner-provisioned client-credentials client restricted to `remote.sessions.revoke` and the exact resource. The client secret also authenticates revocation request/acknowledgement MACs and must be randomly generated with at least 256 bits of entropy. The conductor owns credential generation/storage and client provisioning through the owner's .env procedure; these four fields must be included when updating that existing Secret. Preflight requires all four and a matching HTTPS issuer before any apply. The product manifest explicitly pins `REMOTE_ACTION_ROLE=product`, overriding any shared environment role and refusing missing issuer configuration. Product-only installations outside this paired deployment can omit the remote role/configuration; production evidence refuses activation without revocation composition. The product never mounts the IdP volume or signing key. No new configuration names or provisioning were introduced by F6. Evidence issuance retains its separate internal TLS requirement; revocation delivery uses the authenticated service hop above.

For the evidence backchannel, provision `REMOTE_ACTION_EVIDENCE_CLIENT_ID`, `REMOTE_ACTION_EVIDENCE_RESOURCE`, `OAUTH_ISSUER_URL`, `REMOTE_ACTION_WORKLOAD_ID` and `REMOTE_ACTION_TRUST_FILE`. Public trust has exactly the `idp`, `attestation` and `mesh` pin objects: issuer, kid, workload, secretRef, publicKeyPem and optional revoked. Private evidence keys must be separate mounted secrets; the product must never mount the IdP key. The caller's S2S client must be the attestation workload. TLS termination must supply an authenticated internal TLS route; untrusted forwarded headers do not authorize it.

It returns only the pinned native audience and exact tenant/workspace or null. The issuer then checks its own current membership.
