## Architect double-consensus (2026-08-01, code-verified, `claude:s-archi`)
- **F8 — CONFIRMED, 100% client-side, ZERO API.** `agents-feed-adapter.ts` never sets `workspaceLabel` → `AgentsList.svelte:120` falls back to unknown. The current-workspace name is already client-side: `$workspaceScope.items.find(w => w.id === $workspaceScope.selectedId)?.name` (pattern `InitiativeDetail.svelte:126`, `OrganizationForm.svelte:76`). Pass it into the adapter input → set `AgentsEntry.workspaceLabel`. **GO client-side, no consensus needed beyond this confirm.**
- **F1 — APPROVED as additive-minor own-principal API endpoint.** Data model already supports it (`chat_sessions_user_id_idx`). Only gap: `GET /sessions` today calls `listSessions(user.userId, user.workspaceId)`. Minimal change = ONE additive server variant `GET /sessions?scope=all` → `listSessions(user.userId)` **without** the workspace filter, own-principal (listing your own sessions across your workspaces is always authorized, P1). Labels are FREE client-side: each session carries `workspaceId`, client already has `$workspaceScope.items` → map `workspaceId→name` (same store as F8). **Do NOT** compose per-workspace client-side (endpoint scopes by context ws, not a param → would need its own API change + N calls, strictly worse). **Caveats:** (1) keep ordering + a **bounded default/pagination** in the all-ws variant; (2) the whole server change is `chatService.listSessions` accepting a userId-only path (drop the WHERE workspace clause). **Remove the in-app dev message regardless** — the toggle works (via the endpoint) or is hidden, never a dev justification shown.
