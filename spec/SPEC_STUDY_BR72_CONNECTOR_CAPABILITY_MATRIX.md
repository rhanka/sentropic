# SPEC STUDY — BR-72 Connector Capability Benchmark Matrix

Status: **CONSENSUS REVIEWED (Opus 4.8xhigh + gpt-5.6-sol xhigh)** — WP-CATALOG deliverable named by SPEC_STUDY_UNIVERSAL_CONNECTOR_ACCOUNT_BROKER.md §8.3. Non-product, non-implementation. This is a **benchmark/taxonomy** artifact, not a build queue or adoption plan.

Owner directive (2026-07-15): OOMOL open-connector is a **taxonomy-only** corpus. Sentropic connectors are **recoded** against Sentropic-owned MCP platform contracts. wrap/import is **forbidden** as an OOMOL-row disposition.

## 0. Purpose

Ground the Sentropic connector catalog against a large existing ecosystem (OOMOL open-connector, **1,090 providers / 11,136 actions**, Apache-2.0 in OOMOL `LICENSE.txt`) before Sentropic invents new connector shapes. Output = a capability matrix + gap list that guides Sentropic-owned recoding, keyed to our contracts:

- @sentropic/mcp-platform manifest.ts: AppCapability, CapabilityResource, CapabilityTool (including category, mutability, mutatesExternalSystem, and idempotency), CapabilityPrompt, ConnectorSecretRequirement.scope (operator|principal|tenant|workspace|connector-instance), and CapabilityGates (requiresElicitation|requiresHumanConfirmation|requiresPrincipalGate|requiresPolicy).
- runtime.ts: StpConnectorContext, AppConnectorProviderAdapter, SecretStatus, DurableCall (async/long-running), and AppInvocationEnvelope.
- Resource-Plane vocabulary: ResourceRef plus separate discover, read, and invoke permissions, with deny-as-missing visibility.

## 1. Source taxonomy (OOMOL open-connector, ground truth)

Pinned corpus clone commit: **f36dcbf324a3915e5f6e6b97a20f08d2e18c1172**.

Verified from src/core/types.ts and provider definitions:

- **Providers**: 1,090 directories under src/providers/<service>/, each with actions.ts and definition.ts.
- **AuthType** = "no_auth" | "api_key" | "custom_credential" | "oauth2".
- **ActionDefinition** = { id: "<service>.<name>", service, name, description, requiredScopes[], providerPermissions[], inputSchema, outputSchema, followUpActions?, asyncLifecycle? }.
- **ProviderDefinition** = { service, displayName, categories, authTypes, auth, actions } (the required fields at types.ts:198; it has no id field).
- Signals mapped to the target contracts:
  - asyncLifecycle → a DurableCall candidate (long-running / durable execution).
  - followUpActions → advisory workflow/follow-up capability chaining.
  - requiredScopes and providerPermissions → capability authorization requirements and gates.
  - inputSchema / outputSchema → CapabilityTool input/output schemas.
  - authTypes → credential custody alternatives; not a provider authorization decision.

## 3. Matrix column schema (per §8.3)

Rows are providers and, only for the first wave, individual actions. The wide per-action table is deliberately scroll-oriented.

| Column | Source | Target meaning |
| --- | --- | --- |
| target capability kind | action shape | resource, tool, or prompt |
| CapabilityTool.category | operation semantics | read, write, workflow, or transaction (— for a resource) |
| mutability / external mutation | operation semantics | closed Mutability plus explicit mutatesExternalSystem |
| idempotency | operation semantics | idempotency.required, including its scope; every read-only row explicitly states false |
| gates | write risk | requiresHumanConfirmation / requiresPrincipalGate / requiresPolicy (HC / PG / Policy) |
| RedactionClass | conservative maximum output sensitivity | none|low|moderate|high|secret |
| secret scope | provider authTypes | ConnectorSecretRequirement.scope and handle-first custody |
| execution-projection | target capability kind | resource read / resource list / resource grep, or tool invoke |
| required-authorization | Resource-Plane permissions | any applicable combination of discover, read, and invoke; these are not exclusive labels |
| deny-as-missing note | capability visibility | unauthorized capability/ref is absent from discovery, not merely rejected after selection |
| audit/trace feasibility | schemas and invocation | feasibility of a ToolInteractionTrace / audit id with redacted refs |
| provider API ToS | legal review | unverified unless the third-party API terms were reviewed; OOMOL's Apache-2.0 license does not cover an API |
| disposition | Sentropic decision | §4 vocabulary only |

## 5. Reproducible method (harvest → map → gap)

spec/br72/harvest.mjs is the committed deterministic parser/normalizer. It loads static ProviderDefinition catalog declarations only (never executors), makes no network request, and writes:

- spec/br72/providers.tsv: exactly one row per provider — service, primaryClass, authTypes, actionCount, asyncActionCount, followUpActionCount, distinctRequiredScopes, top3Verbs.
- spec/br72/digest.txt: the SHA-256 of providers.tsv, headline counts, raw/bucketed verbs, and the verb/class keyword maps used for this corpus.

From a clone with its declared TypeScript dev dependency installed:

    node spec/br72/harvest.mjs /absolute/path/to/open-connector --write
    node spec/br72/harvest.mjs /absolute/path/to/open-connector --first-wave

The normalizer strips the service prefix and dotted namespaces, takes the final name segment, splits underscore/hyphen/camelCase, and uses the first semantic token. add, remove, clear, and generate have explicit per-action semantic overrides; none is blanket-mapped to an append/create/delete mutability. The generated first-wave output is the source of §7, not a hand sample.

## 7. First-wave per-action deep-dive

This is the exhaustive generated first wave: **145 GitHub + 43 Google Drive + 46 Gmail = 234 rows**. There is no umbrella googleworkspace provider in the corpus, but substantial Workspace coverage exists via separate providers: gmail, googlecalendar, googledocs, googledrive, googleforms, googlesheets, googleslides, googletasks (+ googlephotos). npm and wave are genuinely absent and have no close functional substitute; no rows are fabricated for them.

Parameterized/paginated list/search actions are read-category tools unless a stable URI template and pagination contract are proved. A typed search/list tool therefore has tool invoke as its execution-projection and normally requires discover+invoke: invocation and visibility of returned resource refs are separate permissions. resource is reserved for a URI-addressable single-entity read. No first-wave OOMOL row maps to a prompt.

HC, PG, and Policy abbreviate requiresHumanConfirmation, requiresPrincipalGate, and requiresPolicy. All provider API ToS entries remain unverified; Apache-2.0 in OOMOL `LICENSE.txt` is solely the corpus license.

## 8. Contract-gap findings

All directions below are **PROPOSED**, additive only, and authorize neither a connector implementation nor a dependency on the source corpus. Every proposed structure is optional/sibling and must route through ./experimental first. None may (a) make selectedAuthType required on ConnectorEnrollment, (b) widen invokeTool's return union, (c) change validateSecrets() away from status-only, or (d) modify canonical DurableCall.

| Proposed finding | OOMOL construct | Sentropic-side gap | Additive direction |
| --- | --- | --- | --- |
| **PROPOSED: provider permission requirements** | providerPermissions[] on 949 actions; 780 also have requiredScopes. | CapabilityTool.requiredScopes is a string list and gates are booleans; neither preserves provider-native authorization. | Add tagged, capability-keyed requirements — oauth-scope, provider-role, or api-permission — applicable to resources as well as tools; project them to authorization/gates without copying raw provider fields. |
| **PROPOSED: follow-up capability graph** | 262 actions declare 360 followUpActions[] references. | durability.workflowBackedTools has no per-capability successor/advisory relation. | Add optional projected follow-ups only after validity/cycle checks; every successor must pass deny-as-missing discovery and an advisory edge must not reveal a hidden capability. |
| **PROPOSED: async action protocol** | asyncLifecycle { startActionId, statusActionId, cancelActionId? } on 100 actions. | DurableCallRef carries a result reference but cannot declare a provider start/status/cancel protocol. | Add an optional experimental descriptor binding provider capabilities to canonical DurableCall transitions, without altering DurableCall. |
| **PROPOSED: credential-field topology** | Custom credentials, API keys, and OAuth client configuration can contain structured fields. | ConnectorSecretRequirement has no field cardinality/sensitivity or secret-vs-public connection metadata. | Add an optional credential-schema extension referencing secret requirement names and separately typed non-secret config; values remain handle-first. |
| **PROPOSED: authentication alternatives (including no-auth)** | 28 providers offer multiple AuthType values; nine advertise no_auth. | Manifest metadata cannot distinguish advertised alternatives from the selected enrollment/runtime mode. | Advertised modes are manifest metadata; selected mode is an optional sibling enrollment/runtime record. Include { kind: 'none' } with egress, abuse, quota, and policy controls; it never bypasses Sentropic authorization. |
| **PROPOSED: OAuth connection bootstrap** | OAuth definitions carry authorization/token endpoints, refresh behavior, PKCE, and client configuration. | Contracts model consent/secret status, not broker-facing bootstrap metadata. | Add optional broker or mcp-auth metadata with trusted static provenance, HTTPS/destination policy, redirect restrictions, state/PKCE, redacted token responses, and no private-network redirects; keep it out of the frozen platform root. |
| **PROPOSED: credential verification relation** | custom_credential can nominate testAction { actionName, input }. | validateSecrets() returns only SecretStatus[]. | Permit only a recoded allowlisted read-only capability inside the egress boundary, returning status/account metadata and never raw provider output; validateSecrets() remains status-only. |
| **PROPOSED: canonical pagination** | List actions use provider-specific page tokens/cursors. | No canonical cursor, limit, page stability, or URI-template pagination contract exists. | Add an experimental pagination descriptor for cursor/page token, limit, and stability semantics. |
| **PROPOSED: rate-limit/retry metadata** | Providers expose reset/remaining/retry signals with divergent shapes. | AppResultEnvelope.error exposes only retriable. | Add optional retry-after, reset, and remaining-budget metadata without changing the existing error union. |
| **PROPOSED: field/path-level output redaction** | Outputs can mix identifiers, content, PII, and secrets. | One capability-wide RedactionClass is too coarse for mixed-sensitivity output. | Add optional field/path redaction annotations that retain the existing conservative capability maximum. |
| **PROPOSED: batch/partial-failure semantics** | Batch actions may partially succeed. | A capability has one mutability/idempotency value and no item-result contract. | Add optional batch item-result and partial-failure semantics; do not infer atomicity from the current fields. |
| **PROPOSED: upsert/composite mutation** | create_or_update, upsert_*, and composite mutations occur. | Closed Mutability requires one value even where the provider operation is conditional/composite. | Add an experimental composite/upsert descriptor; github.create_or_update_file is therefore marked gap identified, not statically patch. |
