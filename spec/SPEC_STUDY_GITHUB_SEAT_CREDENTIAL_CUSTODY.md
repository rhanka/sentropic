## 0. Executive summary

Historical (2026-09-20): the mesh/gateway authenticated each provider with a metered API key injected at deploy, while the owner held already-paid seat subscriptions. The study proposed enrolling each seat once, storing the resulting device credential in a GitHub-backed custody store, refreshing it from the Sentropic repository side, and retrieving it at deployment (MEP) so the gateway would run on seat quotas.

Current (on main): the deployable-process contract already specifies that capability beyond the Claude-specific scope. D7 records the owner-selected GitHub Secrets approach, full provider/device payloads, and a dedicated Actions-secret API credential (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:13`, `:144-145`). It specifies a sole scheduled refresher, serialized triggers, GitHub-first durable commit, CAS delivery, failure recovery, and an independent freshness monitor (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:147-153`). PR #659 delivered ordinary Claude-seat enrollment, persistence, refresh, and an injected execution bridge; it did not deliver the general GitHub custody service (§2, §6). The custody job, the projection resolver, and live qualification remain implementation gaps already named on main (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:220`, `:263`, `:410`).

Remaining contribution of this study: the dated owner rationale, the selected custody boundary (§3), unresolved operational questions (§7), and the owner-directed governance amendment (§12). It is not evidence of an implemented or qualified custody service.

Central tension (historical framing, still applicable as history): the broker study bans raw-secret mirroring by default and requires an explicit owner gate, a KMS-to-KMS envelope, an audit trail, and a revocation SLA for any exception (`spec/SPEC_STUDY_UNIVERSAL_CONNECTOR_ACCOUNT_BROKER.md:335`). How the selected design on main relates to that default is stated in §3; no stronger guarantee is claimed there.

## 1. Goal and non-goals

### 1.1 Goal
Historical goal: give the owner a mono-principal capability to run `llm-gateway` on their own paid seats, with credentials that survive redeploys and refresh unattended, without exposing raw seat secrets to agents. Current (on main): that objective is carried by the D7 custody lane (§3-§5); this study adds no second delivery mechanism.

### 1.2 Non-goals (v0)
- No cross-user / cross-agent seat pooling. Scope stays mono-principal, own seats only, personal passthrough with cross-user selection disabled (`spec/SPEC_EVOL_LLM_GATEWAY_LOT2.md:249`). No categorical provider-permission assurance is stated: the later Claude treatment distinguishes the recorded owner continuation decision from provider permission (`spec/SPEC_EVOL_LLM_MESH_CLAUDE_SEAT.md:63-75`, `:260`).
- No agent-visible refresh tokens, cookies, 2FA codes, or security-key material. Policy/index, custody, and human-challenge boundaries are already established on main (`spec/SPEC_STUDY_UNIVERSAL_CONNECTOR_ACCOUNT_BROKER.md:267`, `:329-335`, `:366-380`; `spec/SPEC_EVOL_LLM_MESH_ACCOUNT_ADMINISTRATION.md:16-44`).
- No new authorization plane: reuse the existing policy/index and account-administration contracts cited above.
- No unconditional metered fallback: fallback requires explicit configuration, matching owner/workspace authorization, and reserved budget (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:163`); no implicit fallback follows a seat failure (`spec/SPEC_EVOL_LLM_MESH_CLAUDE_SEAT.md:187`, `:258`). The CI-seats lane keeps its own seat-only cost constraint (`spec/SPEC_EVOL_CI_SEATS.md:5-6`); that lane rule is not a blanket rule for every gateway consumer.

## 3. Selected custody boundary — GitHub Secrets

The owner-selected store is GitHub Actions repository secrets in the private common custody repository (Q3=B, §11.2). The earlier encrypted-blob and handle-only alternatives are superseded and removed. GitHub stores the full provider/device payload; only the authorized access projection is delivered to consumers. The sole refresher and central placement are fixed, not questions to resubmit.

Decision recorded on main (current): the later owner decisions supersede the ciphertext/materializer model with GitHub Secrets updated by API, one scheduled Actions refresher that also delivers to preprod, and provider revocation per device (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:13`). Full provider/device payloads and the dedicated Actions-secret API credential are specified at `spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:144-145`. Preprod delivery is ratified and production delivery is deferred (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:155`, `:263`); the bounded decision and its provisioning prerequisites are carried forward without reopening them and without treating them as production authorization.

Security boundary (current, corrected): encryption at rest and a runner ability to decrypt are different boundaries. The selected Secrets design entrusts full credentials to the GitHub secret/job boundary (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:144-147`); no guarantee that GitHub cannot decrypt the credentials follows. The broker stricter default remains at `spec/SPEC_STUDY_UNIVERSAL_CONNECTOR_ACCOUNT_BROKER.md:335`; the selected Secrets design is not claimed to automatically demonstrate that KMS-to-KMS condition.

## 4. Refresh loop (Sentropic-repo side)

Current (on main): the scheduled GitHub Actions job is the sole refresher of custody-managed seats. All scheduled and manual refresh and redelivery triggers are serialized, the GitHub Secret update is the durable commit point, delivery uses Kubernetes CAS, post-commit failure retries the same generation without a second rotation, and an independent freshness monitor is required (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:147-153`). Refresh-family identity, authority, epoch, and generation lineage are frozen by the CI-seats contract (`spec/SPEC_EVOL_CI_SEATS.md:18-40`). Failure before a confirmed GitHub commit sets `reauth_required` and alerts the custody operator; operator alerts, freshness refusal, and per-device provider revocation are specified at `spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:151-165`.

The simpler 2026-09-20 loop (iterate seats, refresh, re-encrypt, rewrite with a generic version check) is historical and is not retained as an alternative normative workflow. Schema reconciliation within these established contracts remains the custody lane responsibility (§8).

## 5. MEP retrieval → gateway

Current (on main): delivery is job-only. The custody job creates or updates the Kubernetes seat Secret and delivers an access-only projection; a resolver reads that projection in custody-managed mode and supplies access material only inside the mesh credential boundary. Runtime never refreshes custody-managed seats; no additional token copy may enter application databases, ordinary accounts, or generic exports. The authorized consumer Secret persists an access projection, so this is not a claim that no credential is persisted or backed up. Removed or revoked seats lose local eligibility (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:143`, `:149-163`). Custody projections must not be imported into the ordinary local account service (`spec/SPEC_EVOL_LLM_MESH_CLAUDE_SEAT.md:135`).

The 2026-09-20 description (deploy pulls full credentials into a keyring/pool and seeds active accounts) is superseded and is not retained. Ordinary local seats and custody-managed seats stay distinct; the pool-versus-keyring retrieval choice is decided by the projection resolver above and is no longer open (§7, question 6).

## 9. Risks

- **Custody blast radius (current)**: the selected Secrets design widens exposure to the GitHub secret/job boundary, which holds full provider/device payloads (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:144-147`). The dedicated API credential is a high-privilege provisioning and rotation prerequisite (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:145`).
- **Provider terms (unverified per provider)**: programmatic seat use requires provider-specific qualification. The recorded owner continuation decision is not provider permission (`spec/SPEC_EVOL_LLM_MESH_CLAUDE_SEAT.md:63-75`, `:260`).
- **Reauthentication cliffs**: device/OAuth seats force periodic human reauthentication. Freshness monitoring, operator alerts, and the L3 recovery path are specified; per-repository facade and recovery qualification remain open (§6, Lot C4).
- **Refresh-job target surface**: the sole refresher holds refresh material and is a high-value target. Serialization, GitHub-first commit, and redacted alerts are the specified mitigations (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:147-153`); revocation is per device at the provider (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:165`).
- **Cost model unproven (unverified)**: retained from the 2026-09-20 study. Cost savings and provider-specific applicability remain unverified; provider terms may forbid the exact usage and nullify the saving. The original instruction that validation precedes any build is historical and superseded: O-D1 inherits custody/provider-terms acceptance and adds no legal reapproval gate (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:165`), and terms continuation with the release policy is decided, not a new approval question (`spec/SPEC_EVOL_LLM_MESH_CLAUDE_SEAT.md:63`, `:330`). The existing D7 and Claude qualification gates apply (§6, §8) without reopening the recorded continuation decision.

### 11.2 Target shape

Each repository consumes the appropriate boundary through its authorized CI, CLI, host, or gateway integration; its neutral packages need not import custody. - One custodian writer per seat, as already frozen: only the custodian channel carries renewable material or canonical payloads, and only the custodian holds refresh authority (`packages/llm-mesh/src/enrollment/seat-bundle.ts:15`, `:19`, `:298-313`). A per-repository consumer receives access-only projections, never refresh material (`packages/llm-mesh/src/enrollment/seat-bundle.ts:100-104`, `:301-313`).
- GitHub Secrets remain the durable commit point (D7, §4), held on the central custody host rather than copied into every consumer repository. The store placement is owner-selected, not open: Q3=B (no GitHub Pro) is recorded as binding on main (`spec/SPEC_EVOL_CI_SEATS.md:5-6`), and its recorded consequence is repository Actions secrets in one private common custody repository. That choice is operationally unverified — no provisioning evidence exists on main — and it is not reopened here. D7's older wording, placing the issuance credential in a `custody` environment of one repository (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:145`), is a host binding requiring reconciliation under Lot C0; it does not restore per-repository canonical stores, and no conductor preference reopens the owner choice. An organization-level secret store is not required for all-repository coverage and stays unverified; the GitHub account shape (user vs organization) for the other repositories is not established on main.
- The refresher placement follows the same split: library code shared by all repositories, one central custody host holding the sole serialized refresher authority per refresh family, GitHub-first durable commit, CAS delivery, independent freshness monitor, per-device provider revocation (§4; `spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:147-165`). Repositories are consumers of that host; a schedule per consumer repository would create competing refresh authorities for one family.

Recommendation: build the custody as a library in `@sentropic/llm-mesh`, beside `enrollment/` — the bundle contract, authority model, and enrollment providers already live there — with the access-only resolver consumed by `@sentropic/llm-gateway`, and one thin central custody host that calls the library. Each repository integrates as a consumer through a versioned registry entry; no repository carries its own refresher or canonical secret copy. This follows the owner preference in §11.1 and keeps one custodian implementation and one refresh authority per family for all repositories. This study selects no build start; the lots below are the proposed sequence for the conductor and owner gate.

Mandatory controls for every lot below: admission binds an authenticated repository, workflow, artifact, and purpose to an owner and an allowed seat set — a caller-supplied repository string or `ownerScope` is never authentication; consumer construction receives no publisher or refresher capability or credential; GitHub adapters stay Node-only and outside ordinary or browser imports; projections are materialized from allowlisted fields only; trusted writer/control jobs run separately from native or candidate-code execution. The structural validator alone does not establish these boundaries: `validateSeatBundle` checks shape and caller-supplied context (`packages/llm-mesh/src/enrollment/seat-bundle.ts:137-143`, `:198-199`), and its payload references are opaque strings (`packages/llm-mesh/src/enrollment/seat-bundle.ts:95-103`). Q3=B carries a residual limitation: repository secrets have no per-job secret ACL, so pinned owner-controlled workflows and workflow-contract tests are the compensating control, and a workflow administrator bypass remains a stated residual risk (§9). The test gate must cover foreign-repository or purpose replay, refresh-bearing projection substitution, and writer-secret exposure to candidate or native code.

- Lot C0 — Reconciliation and coordination: dispose every existing owner decision once, preserving Q3=B as owner-selected (§11.2) while reconciling D7's older `custody`-environment host binding and the later local common-repository design input; freeze the consumer registry schema and public exports; coordinate with the open CI-seat import lane (PR #681) before any extraction, so no parallel import, writer, or recovery implementation is created. Provisioning and production activation keep their own gates (G4, O-D3); neither is a new store-choice approval.
- Lot C1 — Custody library core (synthetic first): bundle store, refresh, and projection interfaces in `@sentropic/llm-mesh` over `SeatBundleV1`, with the custodian/consumer authority split enforced on top of `validateSeatBundle` and the mandatory controls above; no live provider or GitHub call.
- Lot C2 — GitHub Secrets adapter and central refresher host: API write with GitHub-first durable commit, serialized triggers, CAS redelivery, redacted alerts; one host runs the same library code for every admitted repository. Minimum invariants: a durable pending fence is persisted before any provider rotation; the committed generation is verified in a newly queued run after the PUT acknowledgement (a queued run can carry a stale secret snapshot, and secret GET returns no plaintext, so serialization alone proves nothing); delivery is tracked per consumer with acknowledgements, and a failed consumer neither blocks nor rolls back delivered ones; after a crash or partial publication, the next permitted operation is derived from the fence and verified generation, with zero replay of old refresh material (extending `spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:149-151` to the repository-secret snapshot protocol).
- Lot C3 — Gateway resolver: the B4 resolver on main (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:220`), reading the access-only projection; runtime never refreshes custody seats.
- Lot C4 — Per-repository onboarding and authority transfer: register each repository as a consumer with its own binding, policy, and revocation/audit drill; provision the custody credential and rotation on the custody host (`spec/SPEC_EVOL_LLM_DEPLOYABLE_PROCESS.md:145`); sentropic preprod first under O-D3, production deferred; then h2a, Engram/Graphify (one adoption entry), immo, design-system, kvm, k8s-ops, and the remaining repositories. Onboarding includes transferring each existing renewable grant to the single custody authority: quiesce the previous refresh holder first (the source CLI and the mesh must not independently refresh the same copied grant, `spec/SPEC_EVOL_LLM_MESH_CLAUDE_SEAT.md:133`), record the transfer, preserve pending generations and revocation state through rollback, and disable replaced schedulers and credentials. Recovery runs through the existing L3 one-command surface (`seat-reenroll`, `seat-replace`, `spec/SPEC_EVOL_CI_SEATS.md:77-89`): guided re-enrollment after native login with no manual secret handling, under the already recorded easy re-enrollment and private-notification decisions (`spec/SPEC_EVOL_CI_SEATS.md:5-6`); no new owner choice is created for that surface.
- Lot C5 — Qualification and release gate: L0b native-profile and lifecycle qualification per CLI (`spec/SPEC_EVOL_CI_SEATS.md:58-68`); crash-recovery drills for interrupted rotation, stale queued-run and re-run, partial writes, and failed consumer acknowledgement, each asserting the next permitted operation and zero old-token replay; five-CLI recovery and notification drills; freshness-monitor drill; per-device revocation evidence. Release gate: freeze the exact package tuple (source and package versions, integrity, public exports — bounded today by `packages/llm-gateway/package.json:44` and `packages/cluster-mesh/src/modules/catalog.ts:17`), prove clean candidate and published installs, and collect exact consumer qualification receipts from at least two independent repository identities and policies; record an onboarding state for every estate entry before claiming rollout completion. Prior npm publication is not a prerequisite for PR #681's separately authorized candidate qualification. No repository advertises custody readiness before its own receipts exist.

### 12.1 G1 — federated contract, one accountable owner per act

Owner decision (2026-10-19, verbatim): **“G1 = option 1”**. Each repository retains its code, release, and data authority. A shared boundary is frozen jointly by its affected owners; only an unresolved material conflict goes to the owner for arbitration. Central approval of every contract change and a provisional pilot-only governance model are superseded.

| Act | Accountable role | Boundary and evidence |
|---|---|---|
| Canonical seat custody and renewal | Sentropic custody maintainer | Owns custody semantics and the single custodian mandate per refresh family; GitHub-first commit, rotation/recovery lineage and provider-device revocation. |
| Custody library code | `@sentropic/llm-mesh` maintainer | Owns the bundle/store/refresh/projection implementation and its versioned exports; does not grant runtime consumer admission by publishing code. |
| Resolver integration code | `@sentropic/llm-gateway` maintainer | Owns the access-only resolver integration and compatibility with the pinned custody contract; no consumer refresh authority. |
| Package release | Respective mesh/gateway release custodian | Owns package versions, integrity and publication receipts; publication does not prove downstream adoption. |
| Custodian runtime | Central custody-host operator | Owns provisioning, serialized jobs, secret access, freshness monitoring and incident drills under the custodian mandate. |
| Consumer admission and data scope | Respective repository's authorized owner/controller | Owns the authenticated principal, permitted seat/family set, purpose, tenant/workspace scope, binding revision and withdrawal; the repository name alone grants nothing. |
| Consumer runtime | Respective repository's host operator | Owns the access-only secret destination, authorized copies/backups and restore/revocation behavior; no writer credential or renewal capability. |
| Consumer acceptance | Respective repository's acceptance owner | Accepts its exact CI/CLI/host/gateway integration using its own policy and lifecycle receipts. |

These are durable roles, not session names; C0/C4 record the actual mandate holders separately even when one person holds several roles. In C0 the custody maintainer, mesh/gateway maintainers, affected host operators and consumer owners jointly freeze delivery and revocation: authenticated binding and purpose, permitted projection fields/destination, schema/package versions and integrity, binding/policy revisions, family epoch/generation, commit/delivery/acknowledgement states, stale/partial delivery, withdrawal versus provider-device revocation, restoration and idempotent recovery. Start from the last accepted boundary; update versioned examples, fixtures and compatibility evidence together, without inventing a second wire schema here. Preserve the last qualified version while a conflict is unresolved; retain each repository's merge/release gates and independent boundary review (C-03/C-08/C-09).

C2/C4/C5 prove the frozen boundary with two independently authenticated repository identities and policies: one rotation, one durable commit, independently acknowledged deliveries, failed-consumer recovery without rotation replay, binding withdrawal distinct from provider revocation, and restore without revoked-material revival. Separate code owner, release owner, operator, controller and acceptance receipts. A transfer records source, receiving owner, accepted destination, reciprocal references, release obligation and remaining consumer acceptance; the outgoing owner remains accountable until acknowledgement (C-11). No new build, rollout, or production GO follows from G1.

### 12.3 H1 — secret exclusion in both artifact modes
