## 2. Design per function

### (b) Browser enrollment — D1: primary path, PKCE with manual return

Mirror **CloudCodeEnrollmentProvider** for session lifecycle and **the existing app Claude enrollment** for manual browser completion. This is real browser authorization: the user signs in and consents on the provider page, then returns the one-use authorization code. It does not require an existing Claude CLI login or a pasted access token. Manual return is explicitly supported by the public CLI/docs (**verified, A1/A2**) and avoids changing the shared loopback helper for a provider-specific callback path.

1. `facade.enroll('claude-code', { configRef, mode: 'cli', redirectUri, ownerScope })` starts browser enrollment. The trusted host supplies the authenticated owner; reject blank owners before opening a session. Resolve D2's configuration, generate a fresh PKCE verifier/challenge and nonce using `pkce.ts`, and allocate an unpredictable enrollment ID. Keep verifier, state, owner, immutable config version, redirect, creation/expiry times, and completion lock only in the provider/service process.
2. Return the existing `authorization-url` session. Compose the URL from the verified/configured fields in the evidence ledger. Use the configured provider-hosted manual callback; a supplied `redirectUri` must equal it (or be empty to select it). No arbitrary redirect supplied by a caller, no client secret, and no browser-side token exchange. The host opens/displays the URL locally, without putting its query into agent transcripts, telemetry, or durable logs.
3. The browser shows `<code>#<state>` (**verified, A2**). A masked local prompt passes that string as `code` to `completeClaudeEnrollment(enrollmentId, code, ownerScopeRef)`. This authorization-code paste is distinct from function (a)'s credential paste. A portal may use the same manual-return flow; an arbitrary portal callback is not implicitly registered with Anthropic.
4. Before any exchange, require the expected provider, matching caller/session owner, unexpired session (15-minute local TTL), matching returned state, nonempty code, and unused/noncancelled status. Reject missing state as well as a mismatch. Atomically lock/consume the session before the asynchronous exchange so concurrent manual submissions cannot exchange twice.
5. POST the JSON exchange shown in A2 using the stored redirect, state, client ID, and verifier. Set bounded request timeout; do not automatically retry a one-use code after an ambiguous response. Validate access/refresh tokens as nonempty strings, expiry as finite positive `expires_in`, and returned scopes against the profile's required subset. Compute ISO expiry from the receipt clock. Never manufacture a refresh token or a one-hour expiry when the provider omitted them. Incomplete grants fail with a sanitized reason and a fresh-enrollment instruction.
6. Convert to `PreparedCredential`, resolve only allowlisted non-secret metadata, and run D4's persistence path. Return only `EnrollmentCompletion` (`accountId`, label). Cancel, timeout, exchange failure, or completion releases session secrets and closes any resources. Restart loses pending sessions and requires a new login; persisted completed accounts survive.

No `waitForCallback`/`pollForCompletion` implementation is needed for the selected manual flow. Leave the existing Cloud Code/Codex methods intact. Automatic loopback is a bounded alternative, not a requirement deferred from browser enrollment: it would need a backwards-compatible callback-path/advertised-host option in `pkce.ts`, local-only binding, bind-error handling, state/replay/timeout tests, and public/live confirmation of the exact redirect. The helper's current fixed `/oauth/callback` must not be silently reused as Claude's verified `/callback`.

### D2: versioned provider configuration, with no guessed values

`ClaudeCodeEnrollmentOptions` follows Cloud Code's `configResolver`/`fetchFn` injection, with an injectable clock for fakes. A versioned profile contains authorization/token URLs, public client ID, manual redirect URI, authorization/refresh/required returned scopes, and source/version provenance. Recommend bundling A2's `claude-code-oauth-2.1.80-v1` pending O3. At enrollment/import, an absent provider resolver or empty result (`{}`) selects that bundle; a nonempty invalid result or resolver exception fails closed. This deliberately diverges from Cloud Code/Codex silent fallback (`cloud-code.ts:153–170`; `codex.ts:48–58`). The facade still requires its existing resolver; no factory contract change.

Start with A2's measured normal-login scope set and refresh scope set. That matches a known client; it does not establish that every scope is necessary. The minimum renewable scope set and current acceptance are **unverified**. A smaller profile must be configured and qualified, not guessed. Do not request an inference-only `setup-token` grant for the full browser requirement because function (c) requires refresh material.

For Claude, `authClientConfigVersion` stores the immutable profile ID in the existing envelope. The service retains it at `local-account-transport-service.ts:501` and passes it as `RefreshInput.credentialVersion` at `:543–547` (default `'v1.0.0'`); it is never a token. Refresh reads that ID, resolves bundled IDs internally without calling the host resolver, and resolves custom IDs only through a validated exact-version host result. Empty/absent resolution may select the bundle only at enrollment/import; it cannot replace a missing custom refresh profile. `'v1.0.0'`, unknown IDs, mismatched versions, or invalid profiles cause `reauth_required` before provider network I/O. Retain old profiles while grants exist; no envelope migration. Runtime header configuration is separately source/version tagged and never derived from pasted data.

### (a) CLI credential paste — D3: renewable credential import

Mirror **MuseEnrollmentProvider**'s validation and **completeMuseDirectImport**'s sessionless service path, without Muse's file reread or key mint. Invoke `completeClaudeCredentialImport(credentialJson, ownerScopeRef)` directly: no enrollment session or method selector. Resolve the trusted host's `claude-code` default profile via D2 and persist its immutable ID; profile selection never comes from the pasted JSON.

Accept either the full JSON document's `claudeAiOauth` object or that object alone. Its verified field names are `accessToken`, `refreshToken`, `expiresAt` (epoch milliseconds), and `scopes`; optional `subscriptionType`/`rateLimitTier` are descriptive only (**verified, A1/A2**). Select known fields explicitly and discard unrelated stores/unrecognized metadata. Reject nonobjects/arrays, malformed/oversize JSON (64 KiB), blank or CR/LF-bearing tokens, missing refresh material, invalid/nonfinite expiry, and scopes missing the configured inference requirement. Recommend accepting a valid past expiry when a refresh token is present (O5): persist unchanged, perform no import-time rotation, and require mesh refresh on first acquire before returning usable material. A failed refresh requires reauthentication.

The trusted input component disables echo/history and bypasses agent/tool-call transcripts, HTTP body logging, tracing, clipboard logging, and exception serialization. The service validates the authenticated owner before delegating to an optional Claude-local `importCredential(credentialJson)` capability, narrowed internally from `EnrollmentProvider`. Keep this capability outside the common contract; no `contracts.ts` edit is needed. `CompleteEnrollmentInput.code` remains exclusively an authorization code for Claude.

A bare access-token paste is deliberately rejected with “Paste the renewable Claude CLI credential or use browser enrollment,” without echoing the value. An access string cannot provide function (c); A1's `setup-token` mode supplies a different access-only product (**verified, A1/A2**). O1 records the access-only product choice and O5 the expired renewable-paste choice. No automatic keychain extraction, shell command displaying credentials, `setup-token` invocation that prints a token, CLI credential overwrite, or new Node credential reader is needed.

### D4: one existing account/persistence path for both functions

Both completions produce an ordinary seat with a random opaque `acct_claude_…` identity per enrolled grant/device, not a hash of secret material or an ID derived from email. Refresh preserves this identity. Multiple separately authorized devices remain distinct; pasting an existing CLI grant does not mint a new provider device (**unverified** provider mapping; treat it as the same grant). Defer identity preservation across re-enrollment: each completion creates a new local identity. Never overwrite by email; importing an already managed grant is an operator error, and these fields cannot reliably deduplicate provider devices.

Use a narrow Claude completion helper in `LocalAccountTransportService`: validate the caller owner (and browser session owner), establish/check the existing immutable owner claim and removal barrier, construct the standard account/envelope, persist through `persistCredential`, then make the account eligible. Ensure any temporary registration needed by current persistence bookkeeping is removed on failure before another acquisition can see it; preferably set bookkeeping without inserting into the executable coordinator. The three writes are not a database transaction: test partial writes, and report success only when envelope/public/index are durable. Preserve existing tombstone semantics.

`resolve` is offline: allowlist validated non-secret fields already supplied by the paste/grant, use `accountEmail` only if present and validated, otherwise label `Claude (<opaque accountId>)`. Labels never determine identity or authorization. The app's profile endpoint `https://api.anthropic.com/api/oauth/profile` (`api/src/services/claude-code-provider-auth.ts:3`) is **unverified** externally; do not call it for enrollment or label resolution.

Metadata is an allowlist: seat billing marker, enrollment method, config version, refresh-management classification for display, and optional validated descriptive subscription fields. It contains no access/refresh token, verifier, code, full profile response, custom headers, or imported JSON. `AccountPublic`, list/remove, route descriptors, and completion remain secret-free. This extends the established persistence path locally; it is not a redesign of every enrollment provider.

### (c) Refresh — D5: authority depends on custody, not provider name

| Account class | Authority and behavior |
| --- | --- |
| Ordinary local Claude seat, enrolled through the facade | `LocalAccountTransportService.acquire` triggers the existing mesh-coordinated single-flight refresh at expiry. The Claude provider uses the envelope's immutable configuration reference and explicit `refreshToken`; it never treats `credentialVersion` as a token. Both browser and paste use the same grant wire. Persist the returned access token, rotated-or-preserved refresh token, expiry, and config reference before exposing refreshed material. |
| Custody-managed Claude seat | The custody job is the sole refresher, exactly as for other custody seats. Browser/import run in a trusted custody enrollment host, using the same provider to prepare credentials; the job commits the full provider/device payload to GitHub Secrets before delivering the access-only projection. The serving resolver verifies the immutable owner claim and reads that projection; it never writes a local keyring envelope or DB token copy, refreshes, or receives refresh material. |

**Shared bug fix, not Claude-only wiring:** `local-account-transport-service.ts:763` clears single-flight before the awaited removal check and `:561` updates `refreshToken`. A concurrent acquire can replay the old rotated token, receive `invalid_grant`, and mark the account `reauth_required`. Widen single-flight through response validation, durable save, removal recheck, and publication; callers must await that whole operation before receiving material. Keep Cloud Code/Codex regression coverage for this window and persistence failures.

The refresh HTTP request follows A2's JSON grant (same endpoint/client, configured refresh scopes). Validate its result as strictly as enrollment; retain the prior refresh token only when the field is absent, reject an explicitly empty/malformed replacement, and preserve account identity/config binding. Terminal `invalid_grant`/revocation, missing material, unknown config version, or irreconcilable persistence failure becomes `reauth_required`; provider errors expose only an allowlisted error code and HTTP status. Do not replay old refresh material after an ambiguous rotation. The existing service marks all refresh failures reauth-required; keep that conservative behavior for this minimal lot rather than broadening retry policy.

Ordinary single-flight is process local. Run one credential-owning service per grant; two processes or the source Claude CLI and mesh must not independently refresh the same copied grant. Prefer browser enrollment for unattended mesh use; paste requires the operator to transfer refresh ownership away from the source session. Do not silently synchronize two credential stores. A distributed lease protocol is outside this minimal package change.

Custody enforcement is a separate host responsibility, not a caller-supplied metadata flag: do not import a projection into `LocalAccountTransportService`, whose existing acquire path refreshes expired accounts. Feed access-only `ClaudeCodeAccountAuthMaterial` through the custody resolver/opaque route attempt instead. The current checkout has the controlling design but no implemented resolver to cite as a working guard. Before enabling custody Claude seats, the custody/deployable-process lane must prove expired/stale projection refusal, zero provider-token calls from runtime, fresh-projection reload, GitHub-first commit/idempotent delivery, and no token in DB/backups. Until then only the ordinary local path can be qualified; do not advertise custody readiness.

### D6: separate runtime lot, using the existing Anthropic adapter seam

Implementation lot 2 adds `ClaudeCodeRuntimeClient implements AnthropicAdapterClient`, scoped to **CodexRuntimeClient/MuseRuntimeClient** parity: injected fetch, per-request auth, `generate`/`stream`, abort handling, status/retry hints, and existing mesh response/events. Inject it with `createDefaultProviderAdapters({ anthropic: client })`; route acquisition supplies auth context. Keep `LlmMeshFacade.getAdapter`'s Cloud Code-specific interface unchanged. Lot 1 enrollment/refresh/persistence must be independently testable without this client.

Accept only generic `account-transport/provider: claude-code` and existing access-only `claude-code-account`; refuse other transports. A private `buildClaudeCodeAuthHeaders` inside the runtime client handles both shapes and sends Bearer, `anthropic-version`, configured source-backed betas, JSON content type, and an honest mesh User-Agent to A3's endpoint. Keep `adapter-auth.ts` unchanged, including generic validation's `{ ok: true }` without headers. Remove `x-api-key` case-insensitively; construct auth after safe extra headers. Never forward arbitrary stored/request headers or credentials to redirects. Base URL overrides are trusted host configuration; tests inject fakes.

Translate the supported mesh surface to Messages: system/user/assistant content, tool definitions/input schema, tool-use/results with IDs, tool choice, and `max_tokens`. Decode text, supported thinking/signatures, tool JSON deltas, usage, finish reasons, errors, and aborts for `generate`/`stream`. Map images/reasoning only where the existing mesh contract supports them; otherwise reject before I/O. No full Anthropic SDK/feature parity, new model controls, or routing subsystem is required. ## 4. Security — D8

- **Secret handling:** access/refresh tokens, pasted JSON, authorization codes, verifier, callback query, and token responses never enter logs, stdout/stderr, traces, exceptions, snapshots, issue/agent messages, commands/argv, source files, or commits. Only the local trusted input component sees the paste. Redaction is defense in depth: emit status and allowlisted reason codes instead of copying remote response bodies, SDK error objects, or network errors carrying a request. Test reflected secrets, malformed JSON, aborts, and storage failures using distinctive fake canaries.
- **Enrollment boundary:** validate the caller owner before parsing/exchanging; browser completion additionally validates session owner, state and TTL, with one-use consumption and a completion lock. Recheck cancellation/expiry/ownership after network completion and before persistence. A cancelled browser request cannot publish an account; sessionless import has no session to cancel. Memory cleanup is best effort in JavaScript, not physical zeroization. Browser authorization URLs may be opened locally but should not become durable evidence.
- **Ordinary storage:** reuse encrypted envelopes and immutable owner claims. The file keyring uses a 0700 directory, 0600 records/master key, AES-GCM and atomic replacement (`packages/llm-mesh/src/node/keyring/encrypted-file-keyring.ts:86`, `:128`, `:145`). The adjacent master key means encryption does not protect against a compromised user account or a backup containing both files. Portal production hosts must supply a durable appropriate keyring; the facade's default portal memory store is not durable. Do not use `EnvKeyring` for these imports.
- **Custody storage:** reuse the job/projection design: full secret stays with the custody owner; serving receives access-only material inside the resolver boundary. No refresh token, GitHub credential, second token store, DB token write, or backup copy in serving. A locally persisted owner claim is an authorization binding, not proof that a provider subscription is valid.
- **Rotation/failures:** require one refresh authority per grant, including the source CLI after a paste. Preserve a newly rotated result through durable save before eligibility; if rotation outcome/save cannot be reconciled, stop using the grant and require operator reauthentication. Removing an account during refresh must prevent its resurrection. No speculative endpoint/header retries, automatic metered fallback, or logging of the stale/fresh credential for comparison.
- **Revocation:** operator revokes the selected device at the provider, then removes/disables that local/custody account and confirms its access and refresh fail while another device remains usable. Local `removeAccount`, deleting a file/Secret, or `/logout` alone is not evidence of provider-side per-device revocation. Exact Claude mechanism and propagation bound are **unverified**; the operator records only device reference, time, outcome, unaffected-device check, and the measured delay. Never roll back known-revoked credential material.
- **Terms:** **verified (A4)**, current public documentation restricts third-party subscription OAuth login/intermediation. The owner assumes usage as specified in the brief; no legal reapproval question is introduced. That assumption does not establish Anthropic authorization, stable service availability, or permission to impersonate the official client. Provider policy enforcement remains a delivery risk, and third-party subscription serving remains **unverified** until measured.
