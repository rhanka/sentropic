# SPEC_EVOL — h2a Into Sentropic Integration (Orientation #3: Remote)

## 0. Status and purpose

This is the design-only D6 specification for orientation #3 (remote) of capitalize-sentropic. It realizes BR-39l, **h2a sessions in the Sentropic UI**, and builds on the one-surface fusion contract in sentropic PR #502, `spec/SPEC_EVOL_AGENTS_SURFACE_FUSION.md`.

No lane or build is authorized. The storm-gate remains h2a runtime 0.90.1. Every integration build is additionally gated on every relevant deferred security/contract primitive in §4.C being published and pinned **and** on an owner signature obtained and read back through the satisfied Part-3 decision flow. This document is neither that signature nor permission to merge implementation.

The governing invariants are `surface/I1` through `surface/I5` in h2a's sole publisher, `docs/governance/surface-invariants.md` (h2a PR #152). This specification references that publisher rather than pinning a second copy. In particular, the in-force `surface/I5` is: “un échec ne doit jamais ressembler à un succès ; distinguer FAIT / DÉPOSÉ-EN-ATTENTE / PAS-FAIT ; refuser est le défaut LÀ OÙ accepter honnêtement est impossible.”

## 1. Governing criterion: absence of debt

Every capability in this integration MUST capitalize on an existing Sentropic primitive. A new h2a-side concept that shadows one is architectural debt and is refused.

## 2. The three parts

### Part 1 — Code-spaces are code workspaces

A code-space—a repository checkout or worktree where agents operate—is enrolled as an existing Sentropic workspace with `type:'code'` and ordinary membership. The one explicit enrollment binding is `H2AWorkspaceRef.id -> workspaces.id`, following the connector-account-enrollment pattern: the Sentropic-owned enrollment row is unique on `H2AWorkspaceRef.id` and points to exactly one `workspaces.id`. `H2AWorkspaceRef.id` is the sole durable workspace identity that crosses the h2a/Sentropic boundary (`surface/I1`), never an h2a session or conversation id; `workspaces.id` remains Sentropic-internal.

Enrollment lookup is idempotent and keyed only by `H2AWorkspaceRef.id`: requests from h2a carry that id, Sentropic resolves it through the enrollment row to `workspaces.id`, and responses or later events crossing back carry the same `H2AWorkspaceRef.id`. Label or checkout-path matching is FORBIDDEN, as is silently retaining two unbound workspace identities. Authorization is workspace membership plus real tenant resolution. Sentropic product code MUST call the DB-backed resolver introduced by PR #416 at `api/src/services/tenancy/resolve-tenant.ts`, MUST set `TENANT_RESOLUTION_MODE=strict`, and MUST add production cache invalidation/TTL or perform fresh per-authorization resolution before trusting a positive result. Strict mode alone MUST NOT open the authorization gate, and a workspace id MUST NOT be treated as a tenant id. PR #439 is relevant only for making the mcp-platform `TenantResolver` seam async. Cross-repo integration remains CLOSED until P1-A publishes and pins the co-specified production authorization port **and** both strict mode and fresh authorization behavior are in force; the `@sentropic/mcp-platform@0.1.1` testing subpath is not eligible. **LIB:** Sentropic exposes the workspace-enrollment surface and owns the binding row over its workspace primitive. **INTEGRATION:** h2a submits and retains `H2AWorkspaceRef.id`. Wire/schema and published authorization-port details remain co-specified with their primitive owners (§6), but they MUST preserve this binding and idempotency rule and cannot introduce a shadow model.

### Part 2 — Remote CLI sessions are visible

This part is BR-39l. `@sentropic/h2a@0.91.0` is h2a's PUBLISHED feed producer: `readLocalFeed -> H2AFeedResponse` already reads registrations plus presence, refuses partial or unreadable inputs, and preserves measured freshness. `H2AFeedResponse` is exactly `{asOf, instances, sessions}` and publishes no feed-level provenance property. This design adds none; any future adapter-origin marker is an endpoint-owned assertion, not a measured value, unless a pinned future h2a version publishes feed-level provenance.

The co-specified Sentropic endpoint MUST consume both descriptor arrays through the ONE `AgentsFeedPort` from #502, with one row per current descriptor. Before durable identity repair, every `InstanceDescriptor` produces a root `AgentsEntry{kind:'remote'}` keyed ephemerally on `instanceId`; chat-ui defines `remote` as read-only and it is explicitly NON-DURABLE here. Every `SessionDescriptor` produces a contained `AgentsEntry{kind:'session'}` whose `parentId` is the descriptor's `instanceId`. No current instance may be labeled perennial or projected as `kind:'agent'`. The endpoint MUST NOT re-read raw presence, reconcile another descriptor input, rebuild h2a descriptors, or collapse either array. It remains an own-principal surface: Sentropic authenticates its caller and uses the PR #416 API resolver only with **both** `TENANT_RESOLUTION_MODE=strict` **and** production cache invalidation/TTL (or fresh per-authorization resolution). Strict mode alone does not open this gate, and the cross-repo dependency remains CLOSED until P1-A publishes the production authorization port and the two-part tenancy requirement is satisfied.

The projection is an **exhaustive per-field mapping with explicit sentinel handling**:

| Current `InstanceDescriptor` field | `AgentsEntry` / `remote-evidence/v1` target |
|---|---|
| `instanceId` | `id = instanceId`, root `parentId` absent, plus `descriptor.instanceId`; the id is conversation-bound and ephemeral. |
| `displayName` | Required `title = displayName`. |
| `host` | Base `hostKind = host`. |
| `role` | `descriptor.role`, retaining the literal `unknown`; display-only, never authorization. |
| `workspaceLabel` | Base `workspaceLabel`. `workspaceId` comes from Sentropic's authorized enrollment scope, not from the feed. |
| `declaredCapabilities` | Instance-only evidence field `declaredCapabilities`, unchanged after h2a's vocabulary sanitization; display-only. |
| `lastSeen` | Required numeric `lastActivityAt` by the timestamp rule below, plus raw `measurement.observedAt = lastSeen`. |
| `liveness` | Required `status` and optional `connection` by the table below, plus exact `feedState.liveness`. The consumer never recomputes it. |

| Current `SessionDescriptor` field | `AgentsEntry` / `remote-evidence/v1` target |
|---|---|
| `sessionId` | `id = sessionId`, plus `descriptor.sessionId`. |
| `instanceId` | `parentId = instanceId`, plus `descriptor.instanceId`. |
| `topicOrTitle` | Required `title = topicOrTitle`. |
| `state` | Required `status` by the table below, plus exact `feedState.sessionState`. |
| `openedAt` | `descriptor.openedAt`, retaining ISO text or the literal `unknown`; it does not replace activity time. |
| `lastActivityAt` | Required numeric `lastActivityAt` by the timestamp rule below, plus raw `measurement.observedAt = lastActivityAt`. |
| `activitySource` | Exact `measurement.activitySource: 'mcp' | 'heartbeat'`; advisory `heartbeat` is never upgraded, displayed, or authorized as proven `mcp` activity (`surface/I2`). |
| `counterpartsOpaqueRefs` | Exact `descriptor.counterpartsOpaqueRefs`; no de-opacification or routing use. |

| h2a instance `liveness` | `AgentsEntry.status` | `AgentsEntry.connection` |
|---|---|---|
| `live` | `active` | `connected` |
| `idle` | `idle` | `unknown` |
| `stale` | `idle` | `unknown` |
| `closed` | `done` | `disconnected` |

| h2a session `state` | `AgentsEntry.status` |
|---|---|
| `open` | `active` |
| `idle` | `idle` |
| `closed` | `done` |

The mapping never invents `awaiting-input`, `running`, or `failed`, because the current h2a descriptors do not assert those states. `liveness:'idle'` proves that the process lives but proves no MCP-channel traffic, so it retains exact `feedState.liveness = 'idle'` while mapping to `status = 'idle'` and `connection = 'unknown'`. The same no-connectivity inference applies to any future published `idle-uncertain` or `unknown` liveness sentinel. Only a future pinned h2a field that separately proves link connectivity may yield `connection = 'connected'`. `stale` is not redefined as semantic idle: the compatible base status is `idle`, while exact `feedState.liveness = 'stale'` and `connection = 'unknown'` preserve the feed's uncertainty.

Timestamp handling is deterministic. A descriptor timestamp containing valid ISO 8601 maps to the same instant as numeric epoch milliseconds in base `lastActivityAt`, while the original ISO value remains in evidence. The literal `unknown` maps to numeric `0` only because published `AgentsEntry` requires a number; evidence retains `measurement.observedAt = 'unknown'`, and consumers MUST treat `0` as a projection sentinel, never display it as a genuine 1970 observation or freshness claim. Envelope `asOf` is preserved separately as `measurement.asOf` and MUST NOT replace `lastSeen`, `lastActivityAt`, or `openedAt`. Any other unparseable value is a contract violation and fails the projection rather than dropping a row.

The following evidence fields are **ADDED-BY-A-FUTURE-SLICE**; none is present in `@sentropic/chat-ui@0.33.0`. They form additive contract `remote-evidence/v1`, produced by the BR-39l Sentropic projection endpoint and consumed by the #502 `AgentsFeedPort`/agents surface. Receivability requires their publication in an explicitly pinned `@sentropic/chat-ui` version later than 0.33.0:

- `agentRef`: the slot is reserved for durable remote-agent identity under `surface/I1`, but it is GATED and MUST remain absent/unpopulated for current `@sentropic/h2a@0.91.0` and 0.91.1 input. Those feeds bind identity to `(host, providerSessionId)` and cannot make two provider conversations collapse to one durable-agent row. Until a future published `@sentropic/h2a` version repairs the `reclaimOrMint` resume path and exports an explicit cross-conversation perennial identity field, Part 2 emits only non-durable `kind:'remote'` instance roots plus their session rows. Once shipped and pinned, only that durable `agentRef` may key a perennial `kind:'agent'` root; current `instanceId` and `sessionId` never may.
- `descriptor`: the discriminated descriptor-only evidence enumerated in the tables above, including identity, role, opened-at sentinel, and opaque counterpart references.
- `measurement: { observedAt, asOf, activitySource? }`: preserves the descriptor-specific ISO observation or literal `unknown`, the response-envelope `asOf`, and—on session rows only—the exact MCP-versus-heartbeat provenance; it contains no adapter-origin measurement.
- `feedState: { liveness?, sessionState? }`: instance rows carry exact `liveness`; session rows carry exact `state`. These are the authoritative raw feed values behind the compatible base status/connection mapping.
- `authority: { holder, mode:'VIEW' }`: the remote CLI host is HOLDER and the Sentropic row is VIEW; the agents surface consumes it to preserve read-only foreign authority (`surface/I3`).
- `declaredCapabilities`: mapped from `InstanceDescriptor` only to its current non-durable `kind:'remote'` row, constrained to h2a's closed, sanitized `H2A_DECLARED_CAPABILITIES` vocabulary (`surface/I4`).

Self-declared display capabilities are NON-AUTHORITATIVE and MUST NEVER grant, imply, or widen authorization. Connector-host capability exposure remains solely the Sentropic-internal MCP authorization path; there is no mapping from `declaredCapabilities` into that allowlist. Sentropic may reuse connector-host account/workspace exposure internally for the remote host attachment, but #492 supplies only BEST-EFFORT / FAIL-OPEN capture-before, tombstone/outbox-during, and revoke-after-commit teardown; none of those steps blocks deletion on failure. This integration MUST NOT rely on #492 for a fail-closed durable-teardown or no-orphan security guarantee. Any attachment security gate that needs that guarantee remains CLOSED until a published fail-closed teardown contract is co-specified and pinned. h2a consumes only the co-specified published/HTTP boundary and no connector-host dependency.

Every remote operation reports `FAIT`, `DÉPOSÉ-EN-ATTENTE`, or `PAS-FAIT` according to `surface/I5`. An unreachable holder can accept a durable deposit only when that acceptance is honest; otherwise the operation refuses as not done. The api/h2a join and endpoint are gated on runtime 0.90.1 and owner signature.

### Part 3 — Decision dossiers under Sentropic; signature through Focus, not chat

Published `@sentropic/h2a@0.91.0` produces `H2ADecisionDossier`, but that object is not the Track `Dossier`/`DecisionDossierView` that published `@sentropic/focus@0.3.0` accepts and renders. Current Focus does **not** render `H2ADecisionDossier` content. This design pins one intended boundary: a future co-specified, published h2a-to-Track dossier adapter/wire MUST transform `H2ADecisionDossier` into a Track-native `Dossier`, while retaining the h2a dossier as the existing opaque artifact pointer (`negotiationRef`/`dossierHash`) and comprehension-metadata source. Until the adapter/wire's exact published contract and version are pinned, Part 3's dossier-rendering dependency is CLOSED and no direct h2a-dossier submission is receivable.

After that boundary opens, h2a submits through the pinned adapter/wire and reads the Track outcome. Focus renders only the resulting Track-native decision view and may record an outcome in Track, but that outcome is an owner SIGNATURE only after the separate Part-3 live-write security gate below is co-specified and satisfied. The signature is the durable decision id plus the owner's MEASURED authenticated act (`surface/I1` and `surface/I2`), not a chat utterance, UI click without a write, relayed append, relayer identity, opaque h2a artifact pointer, or fabricated `comprehension[]` evidence.

**LIB:** the Sentropic Focus/Track surface receives and renders only the Track-native dossier produced by the pinned adapter/wire, then security-gates recording and read-back. **INTEGRATION:** h2a submits `H2ADecisionDossier` only through that adapter/wire and reads the recorded outcome, treating it as a signature only after verified read-back of an attested owner act. Current placement is split: Focus already renders Track dossiers read-only, while Track already records decisions; the adapter/wire and live Focus write driver are distinct co-specification gaps, not permission to claim current h2a-dossier rendering or build a new signature UI.

Before Focus live-write may produce an owner SIGNATURE, the co-specified gate MUST define and enforce: the pinned h2a-to-Track adapter/wire; owner/workspace authentication using the own-principal model and the PR #416 API tenancy resolver with **both** `TENANT_RESOLUTION_MODE=strict` **and** production cache invalidation/TTL (or fresh per-authorization resolution), never `shadow` or strict mode alone; authorization for the decision and workspace; ATTESTER-vs-RELAYER provenance, with the owner as attester and any transport as relayer only; a pinned Track ingest contract version; an idempotency key and duplicate-result semantics; and read-back confirmation of the persisted attestation. Until every item is specified, published/pinned where it is a contract, and satisfied, a Track outcome is **NOT** an owner signature.

## 3. Placement and sequencing

Orientation #3 is remote: Sentropic owns durable workspace, exposure, agents-surface, Focus, and Track primitives; h2a remains holder of remote CLI presence and submits integrations into those surfaces. **Part 3 is the priority-first design dependency because it becomes the owner's signature mechanism.** #502 is explicitly pre-signature: neither its merge nor any artifact is an owner signature. Until the h2a-to-Track dossier adapter/wire is published and pinned and the co-specified `FocusLiveSession` owner-authenticated signature gate is satisfied with persisted attestation confirmed by read-back, no owner signature exists and no build lane opens. Part 1 remains near-term in design only, while Part 2 waits for the BR-39l api/h2a join and listing endpoint; its durable `agentRef`/cross-conversation collapse additionally waits for a published h2a identity repair.

The currently deferred Focus live-write driver (`FocusLiveSession` / the live write path) together with its security gate is a co-specification dependency, not an authorized build item in this design: it must close the reuse/composition gap so a Track-native dossier produced through the pinned h2a-to-Track adapter/wire can record a verified owner signature in Track, **not** create a new signature UI. Dependencies remain: #502 for the fused surface; #416 for the internal DB-backed tenancy resolver, whose gate requires both `TENANT_RESOLUTION_MODE=strict` and production cache invalidation/TTL (or fresh per-authorization resolution); #439 only for the async mcp-platform `TenantResolver` seam; #492 only for best-effort / fail-open connector-grant teardown, never as a fail-closed durable-teardown guarantee; h2a PR #152 for the invariant publisher; Focus/Track for decisions. Strict tenancy alone opens no authorization gate. Any security requirement for fail-closed durable teardown remains CLOSED until a published contract is co-specified and pinned. No integration implementation starts before runtime 0.90.1, every primitive relevant to that build is published and pinned, **and** an actual owner signature is obtained, recorded, and read back through the satisfied Part-3 gate; there is no pre-Focus exception. Only after all applicable gates open may Codex TERRA start the approved app/chat/agents lane sequence.
